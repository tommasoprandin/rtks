\section{System Model}
The software architecture of the system under test follows the one proposed in
"\textit{Guide for the Use of Ada Ravenscar Profile in High Integrity Systems}"
\cite{burnsGuideUseAda2004}. It is comprised by one periodic producer task that
activates two other sporadic tasks, depending on certain criteria. Additionally,
there is a sporadic event server that manages the occurrence of external events.
In the implemented application, events are generated by a periodic task that
emulates user interaction, for the sake of repeatability. 

Table [\ref{tab:tasks-list}] enumerates the tasks constituting the
application, together with their type, deadline, period (if applicable) and
priority. Priorities have been assigned using the \textit{Deadline Monotonic}
algorithm, which assigns priorities in decreasing order, starting with the task
having the smallest relative deadline. \textit{Deadline Monotonic} is an optimal
policy for constrained deadlines and fixed-priority scheduling of mutually
independent tasks \cite[p.~119]{liuRealTimeSystems2000}. \\  
The deadline watchdogs, only implemented in the Rust system to cover the missing
support from the runtime, have been given the highest priority in order to
detect overrun without interference from other tasks (see section
\ref{sec:DeadlineMissDetection} for further details).

The tasks in the system share various resources. Access to them is regulated by variants
of the \textit{Priority Ceiling Protocol}
\cite{shaPriorityInheritanceProtocols1990} depending on the implementation: the
\textit{Ada} system implements the \textit{Immediate Priority Ceiling Protocol}
\cite{chengImplementationPriorityCeiling2007}, while the \textit{Rust} system
uses the \textit{Stack Resource Policy}
\cite{bakerStackbasedSchedulingRealtime1991}.\\  
While the implementation is slightly different, both protocols show the same
properties and response-time behavior. They require to specify the ceiling value
for each shared resource, which is obtained by picking the maximum priority
value among all the task using the given resource.

In order to emulate a realistic workload for task requiring some kind of
computation, the small variant of the Whetstone benchmark
\cite{curnowSyntheticBenchmark1976} is used. It includes different kind of
computations: integer, floating-point, trigonometry, branches and function
calls, with the aim of testing the system under a wide range of loads. \\
\label{lab:whetstone-explanation}
The Whetstone benchmark provides a configurable workload parameter that directly 
controls the number of iterations performed by the procedure. Each iteration 
executes a standardized mix of computational operations (floating-point arithmetic, 
trigonometric functions, loops, and conditional statements).
The combination of those types of instructions was obtained from statistical
analysis of common scientific programs at the time of writing of the original
paper \cite{curnowSyntheticBenchmark1976}. In this way, they could obtain a
computational workload that was representative for benchmarking, enabling
abstraction from the specific hardware implementation and providing a
machine-independent measure of computational load through the\textit{Whetstone
Instructions Per Second} (WIPS) metric.
We have ported the \textit{Ada} implementation provided in the original example
\cite{huJiayihuSRT2024} to \textit{Rust}, trying to follow as much as possible 
the original code structure.
By scaling this parameter, we can adjust the worst-case execution time (WCET) of
each task, creating different system utilization levels. 
For instance, doubling the workload parameter approximately doubles the  
execution time, allowing us to systematically stress-test the system. This parametric 
approach enables controlled experimentation where we can observe how the system 
behavior changes as computational load increases, first by simulating it using 
the MAST tool \cite{MASTComprehensiveTool}, then by running the application in 
a real setting.

To this end, we have used the \textit{Olimex STM32\-H405} \cite{olimexSTM32H405}
development board, together with a \textit{STLink\-v2} \cite{STLINKV2Tool}
debugging probe. 

\subsection{Tasks Description}

\subsubsection{Activation Log Reader}

The \textit{Activation Log Reader} is a sporadic task which awaits on a signal
received from the \textit{Regular Producer}, and then performs its internal
operation which consists of a synthetic Whetstone workload, followed by a
reading of the status of the \textit{Activation Log} and a print that notifies
the end of its sporadic activation.

\subsubsection{On-Call Producer}

The \textit{On-Call Producer} is a sporadic task that waits for a request
deposit into the \textit{Request Buffer}, then reads it and runs a Whetstone
workload with load equal to the extracted value. The requests are sent by the
\textit{Regular Producer}, and they are meant to represent a scenario in which a
main task delegates some work to a helper task in the event of an overload. 

\subsubsection{Regular Producer}

The \textit{Regular Producer} is a periodic task that runs a Whetstone workload
with a predefined load value, then, based on a predetermined criterion, can
release the \textit{Activation Log Reader} and send a work request to the
\textit{On-Call Producer}. 

\subsubsection{External Event Server}

The \textit{External Event Server} is a sporadic task that waits for events put
onto the \textit{Event Queue} by the interrupt handler bound to the simulated
external event. It updates the \textit{Activation Log} counter on each
activation. 

\subsubsection{Deadline Watchdogs}

\label{lab:deadline-watchdog-task}
In the Rust system there is no support in the runtime for the detection of
tasks' deadline misses. 
For this reason, we had to manually associate each task in the system with a
watchdog monitor task responsible for checking deadline overruns. It has the
maximum priority to prevent interference. It maintains the number of deadline
misses and whenever it detects one it prints a warning message (see section
\ref{sec:DeadlineMissDetection} for further details). \\
